# Akeng.MauiCrashReporter

Lightweight crash reporting and diagnostics for **.NET MAUI applications**.

Akeng.MauiCrashReporter helps developers capture, persist, and inspect application crashes — including issues that may only appear in **Release builds** and are difficult to diagnose from the application UI.

Instead of manually opening Android Logcat or searching through device logs, the application can persist a structured crash report locally and expose it when the application starts again.

---

## Why Akeng.MauiCrashReporter?

Some .NET MAUI problems are difficult to reproduce during development:

* XAML parsing errors
* Release-only exceptions
* Platform-specific failures
* Lifecycle-related errors
* Unhandled exceptions
* Unexpected application termination
* Errors that are difficult to reproduce locally

The traditional workflow is often:

```text
Application crashes
       ↓
Open Android Logcat / device logs
       ↓
Search through logs
       ↓
Find the exception
       ↓
Try to reconstruct the application state
```

Akeng.MauiCrashReporter simplifies this workflow:

```text
Application crashes
       ↓
Crash is captured
       ↓
Structured report is persisted locally
       ↓
Application starts again
       ↓
Pending crash report can be inspected
```

## Features

### Crash Capture

Captures unhandled application exceptions and builds a structured crash report containing diagnostic information.

### Release-Build Diagnostics

Helps investigate issues that are difficult to reproduce in Debug but appear in Release builds.

This is particularly useful for diagnosing:

* XAML-related failures
* Runtime exceptions
* Platform-specific issues
* Unexpected application termination

### Persistent Crash Reports

Crash reports are stored locally so they remain available after the application terminates.

Reports are stored as structured JSON files.

### Emergency Crash Recovery

A lightweight emergency mechanism preserves critical crash information when a complete crash report cannot be generated.

This allows important information to survive application termination and be recovered during a later application startup.

### Breadcrumbs

Records useful application events before a crash.

For example:

```text
Application started
User navigated to LoginPage
User opened SettingsPage
API request started
User navigated to DetailsPage
Crash occurred
```

These breadcrumbs help reconstruct what happened immediately before the failure.

### Lifecycle Tracking

Tracks relevant .NET MAUI application lifecycle events and associates them with the crash context.

### Session Information

Associates crash reports with the application session in which the crash occurred.

### Environment Information

Collects useful runtime information such as:

* Operating system
* Platform
* Application version
* Device information
* Runtime information

### Crash Fingerprinting

Generates a crash fingerprint that can help identify recurring failures.

For example, multiple reports generated by the same underlying exception can potentially be grouped using the same fingerprint.

### Crash Classification

Provides classification and diagnostic information to help developers understand the nature of a failure.

### Local Storage Management

Crash reports are automatically managed using configurable limits for:

* Maximum number of reports
* Maximum storage size
* Fatal-report preservation

## Basic Setup

Register the crash reporter when configuring your .NET MAUI application:

```csharp
using AkengMauiCrashReporter.Extensions;

public static MauiApp CreateMauiApp()
{
    var builder = MauiApp.CreateBuilder();

    builder
        .UseMauiApp<App>()
        .UseMauiCrashReporter();

    return builder.Build();
}
```

That's it.

The crash reporter is registered through dependency injection and can begin monitoring the application lifecycle and unhandled exceptions.

---

## Configuration

The reporter can be configured during registration:

```csharp
builder.UseMauiCrashReporter(options =>
{
    options.MaxBreadcrumbs = 100;

    options.MaxStoredReports = 20;

    options.MaxStorageSizeBytes =
        10 * 1024 * 1024;

    options.PreserveFatalReports = true;

    options.CaptureLifecycleEvents = true;
});
```

### Available Options

| Option                   | Description                                    | Default |
| ------------------------ | ---------------------------------------------- | ------: |
| `MaxBreadcrumbs`         | Maximum number of breadcrumbs retained         |   `100` |
| `MaxStoredReports`       | Maximum number of locally stored crash reports |    `20` |
| `MaxStorageSizeBytes`    | Maximum storage used by crash reports          | `10 MB` |
| `PreserveFatalReports`   | Prevent automatic removal of fatal reports     |  `true` |
| `CaptureLifecycleEvents` | Enable MAUI lifecycle tracking                 |  `true` |

## Accessing Crash Reports

The `CrashReporter` service can be resolved through dependency injection:

```csharp
var crashReporter =
    serviceProvider.GetRequiredService<CrashReporter>();
```

### Get Pending Reports

```csharp
var reports =
    await crashReporter.GetPendingReportsAsync();
```

Example:

```csharp
foreach (var storedReport in reports)
{
    var report = storedReport.Report;

    Console.WriteLine(
        $"Crash: {report.Exception?.Type}");

    Console.WriteLine(
        $"Message: {report.Exception?.Message}");
}
```

Pending reports are reports that have not yet been marked as processed.

---

## Get the Latest Report

```csharp
var latest =
    await crashReporter.GetLatestReportAsync();
```

The returned report represents the most recently stored crash report.

---

## Get a Specific Report

```csharp
var report =
    await crashReporter.GetReportAsync(reportId);
```

---

## Mark a Report as Processed

Once a report has been inspected or handled:

```csharp
await crashReporter.MarkReportAsProcessedAsync(
    reportId);
```

---

## Delete a Report

```csharp
await crashReporter.DeleteReportAsync(
    reportId);
```

## Clear All Reports

```csharp
await crashReporter.ClearReportsAsync();
```

## Count Stored Reports

```csharp
var count =
    await crashReporter.GetReportCountAsync();
```

## Storage

Crash reports are stored locally by the application.

The local storage mechanism is designed to work offline and does not require:

* A server
* A database
* An Internet connection
* An external monitoring service

This makes the package particularly useful for diagnosing crashes that occur on physical devices.

### Storage Limits

The package automatically manages local storage using the configured limits:

```text
MaxStoredReports
MaxStorageSizeBytes
PreserveFatalReports
```

Older reports can be removed automatically when storage limits are reached.

Fatal reports can optionally be preserved.

## Release-Build Troubleshooting

One of the primary goals of Akeng.MauiCrashReporter is to help investigate errors that appear only in Release builds.

For example:

```text
Debug
   ↓
Application works correctly

Release
   ↓
Application crashes
   ↓
User restarts application
   ↓
Pending crash report is available
```

Instead of relying exclusively on Logcat, the developer can retrieve the persisted crash report from the application.

This can significantly reduce the time spent manually searching device logs.

---

## Offline First

Akeng.MauiCrashReporter does not require network connectivity to capture and store crash information.

This is intentional.

The first priority is to **preserve the crash information**.

Remote transmission can be implemented separately by the application or introduced through future versions of the package.

---

## Privacy

Crash reports are stored locally by default.

Akeng.MauiCrashReporter does not automatically transmit crash reports to a remote server.

If an application later integrates remote crash reporting, the application developer is responsible for determining what information is transmitted and ensuring compliance with applicable privacy requirements.
